# helm 任務狀態 — 設計

**日期**：2026-08-14
**狀態**：設計待核可
**關聯**：2026-08-11-helm-design.md 的 §8（交接簡報）、§11.1（狀態語彙）

---

## 1. 問題

看板現在回答的是「這個 session 的行程還活著嗎」：執行中、等輸入、已結束、已中斷。它回答不了「我交代的那件事做完了沒」。

兩者不同。一個已結束的 session 可能是把事情做完才關掉，也可能是卡在某個地方就沒再回去。看板對這兩種畫的是同一個灰點。

交接簡報（§8）已經有這件事需要的資料：`goal`、`done`、`currentStep`、`nextStep`、`blockers`。缺的是兩件事：

1. 簡報的提示詞開頭就寫「你正在為一個中斷的開發 session 寫交接簡報」，並要求填「回來後應該做的下一件事」。整份提示詞的前提是這個 session 被中斷了，沒有任何欄位允許模型回答「這件事做完了」。因此「`nextStep` 為空即為完成」是一個不會出現的訊號。
2. 簡報的結果只在 `helm brief` 的輸出裡，看板讀不到。

## 2. 目標與非目標

### 目標

1. 簡報能說出這個 session 的任務是完成、進行中、還是卡住
2. 看板在有簡報的 session 上顯示這個狀態
3. 簡報過期時不顯示，而不是顯示過期的結論

### 非目標

- 不主動產生簡報。簡報一次要 57 至 86 秒與一次 LLM 呼叫，看板每 5 秒重畫一次，兩者不能相遇
- 不對沒有簡報的 session 顯示任何任務狀態。本機 156 個 session 中有 3 個有簡報，補一欄「沒問過」等於加 153 行沒有內容的字
- 不改變既有的行程狀態判定。任務狀態與它是兩個維度，不互相取代

## 3. 資料來源與判定

### 3.1 簡報新增欄位

`Brief` 增加 `taskStatus`，值為 `done`、`in_progress`、`blocked` 三者之一。提示詞的 `FIELDS` 同步增加該欄位，並明確允許回答「完成」：

```
"taskStatus": "done（這件事已經做完，沒有下一步）／in_progress（還在做）／blocked（被某件事擋住）"
```

提示詞現有的那句「回來後應該做的下一件事」要改成允許留空，否則模型會為了填滿欄位而編一個下一步出來。

### 3.2 為什麼由模型判定而不是從既有欄位推導

`blockers` 非空可以推出 `blocked`，但推不出 `done`：判定完成需要比對使用者要的東西與實際做出來的東西，那是提示詞裡已有的上下文，模型看得到，程式看不到。多一個欄位不需要多一次呼叫。

### 3.3 舊快取

既有的簡報沒有這個欄位。缺少時視為未知，不顯示任何任務狀態。不需要調整 `CacheShape.version`：多一個選用欄位不影響既有讀取。

### 3.4 新鮮度

`getFreshBriefEntry` 已經用 transcript 的 `<byteSize>:<mtimeMs>` 比對過。transcript 在簡報產生後又變動時，該筆簡報視為不可用，任務狀態不顯示。

顯示過期的「已完成」比不顯示更糟：使用者會據此認為那件事結束了。

## 4. 呈現

### 4.1 顯示位置

任務狀態是 session 層級的資訊，只出現在有列出個別 session 的地方：

| 位置 | 顯示方式 |
| --- | --- |
| `helm sessions <專案>` | session 那一列的後綴 |
| 選單列的 session 子選單 | 同上 |
| `helm brief` 的輸出 | 標題區的一行 |
| `helm status` | 不顯示（一個專案一列，沒有 session 那一層） |
| 桌面 widget | 不顯示（同上） |

### 4.2 用詞

| `taskStatus` | 顯示 |
| --- | --- |
| `done` | 任務完成 |
| `in_progress` | 任務進行中 |
| `blocked` | 任務卡住 |

與行程狀態用不同的詞。行程狀態說的是「已結束」，任務狀態說的是「任務完成」，同一列同時出現時要看得出是兩件事。

### 4.3 組合

兩個維度交叉後，看板才答得出「哪些事沒做完」：

| 行程 | 任務 | 意義 |
| --- | --- | --- |
| 已結束 | 任務完成 | 做完才關掉，不用回去 |
| 已結束 | 任務卡住 | 卡住之後就沒再回去，要處理 |
| 已中斷 | 任務進行中 | 做到一半斷了，有未回收的斷點 |
| 執行中 | 任何 | 任務狀態是上一次簡報產生時的結論，可能已經不準 |

最後一列的處理方式與 §3.4 相同：session 還在跑表示 transcript 一直在變，簡報幾乎必然過期，因此不顯示。

## 5. 錯誤處理

| 情況 | 行為 |
| --- | --- |
| 模型回傳的 `taskStatus` 不是三個值之一 | 視為未知，不顯示 |
| 簡報整份解析失敗 | 沿用 §12 既有的原始提示詞退回方式 |
| `cache.json` 讀不到 | 不顯示任何任務狀態，不影響看板其餘部分 |

三種都不顯示，不猜。

## 6. 效能

看板的快速路徑要多讀一個 `cache.json`（本機 7 KB）並解析一次 JSON。這個檔案在 `helm brief` 執行時才會變動。

實作後要用行程內部的 `process.uptime()` 量 `collectStatus`，確認仍在 §11.2 的 200 ms 內。目前的中位數是 32.3 ms。

## 7. 已知限制

`runClaudeHeadless` 呼叫的 `claude` 在 `~/.local/bin/claude`，不在 launchd 給 GUI 程式的 `/usr/bin:/bin:/usr/sbin:/sbin` 裡，`src/remote/spawn.ts` 的 `TOOL_DIRS` 也沒有收錄該目錄。

目前不受影響：簡報只在使用者執行 `helm brief` 時產生，那是終端機環境，PATH 完整。

日後若改為背景產生，必須先把 `~/.local/bin` 加進 `TOOL_DIRS`，否則會重現 PR 追蹤那次的情況：功能在真實部署下從未成功過一次，而錯誤訊息叫使用者去安裝一個他已經裝好的程式。

## 8. 測試策略

| 對象 | 驗證方式 |
| --- | --- |
| 提示詞 | 包含 `taskStatus` 欄位，且「下一步」允許留空 |
| 簡報解析 | 三個合法值各一條；非法值與缺少欄位都回傳未知 |
| 新鮮度 | digest 不符時不顯示；digest 相符時顯示 |
| 各呈現面 | 有狀態與沒狀態各一條，確認沒狀態時不留下空欄位 |
| 跨面一致 | `src/faces.test.ts` 增加一條：同一個 session 在會列出 session 的兩個面用同一個詞 |

實作完成後對判定與呈現跑變異測試。
